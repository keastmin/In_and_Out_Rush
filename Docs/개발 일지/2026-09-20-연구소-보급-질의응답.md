# 연구소 아이템 구매·보급 질의응답

작성일: 2026-09-20

관련 작업: [연구소 UI 재구성과 개별 아이템 보급](../Work/Completed/W-20260920-002-laboratory-item-supply-ui.md)

이 문서는 연구소 UI와 개별 아이템 보급 구현 후 사용자가 질문한 내용과 코드 확인 결과를 별도로 보존한다. 실제 플레이에서 보고된 증상과 코드상 확인된 조건을 구분한다.

## 질문 1. 생명선과 방벽 외 아이템을 구매할 수 없는 이유

> 현재 생명선과 방벽을 제외한 다른 아이템은 연구소에서 구매가 안되는 이유가 뭐야?

### 답변

기획 데이터 시트의 센터 건설 해금 조건을 구매에 적용했기 때문이다. 시작 시에는 해금 조건이 없는 생명선·방벽을 구매할 수 있다. 다른 아이템은 해당 센터가 존재해야 하며, 해금 후에도 자원과 대기열 여유가 필요하다.

| 아이템 | ID | 광물 | 가스 | 필요한 센터 |
|---|---:|---:|---:|---|
| 생명선 | 7000 | 30 | 0 | 없음 |
| 방벽 | 7001 | 30 | 0 | 없음 |
| 소각기 | 7002 | 30 | 20 | 화염 센터 |
| 전류탄 | 7003 | 50 | 0 | 전격 센터 |
| 생분해 장치 | 7004 | 0 | 60 | 생화학 센터 |

- 기획 출처: `기획/데이터/땅타 프로젝트 데이터 테이블 0.60v.xlsx`, `Item!A4:G9`.
- 설정: [Runner Supply Catalog.asset](../../Assets/08_Data/Runner%20Supply%20Catalog.asset)의 `RequiredCenter`와 `Cost`.
- 판정: [RunnerSupplyRules.cs](../../Assets/02_Scripts/Features/RunnerSupply/Logic/RunnerSupplyRules.cs)의 `Evaluate`.
- 현재 구현은 [RunnerSupplyNetwork.cs](../../Assets/02_Scripts/Features/RunnerSupply/Adapters/Fusion/RunnerSupplyNetwork.cs)의 `RefreshCenters`에서 실제 존재하는 센터를 집계한다. 한 번 건설하면 영구 해금되는 기록 방식은 아니다.

## 질문 2. 시작 직후 보급타워에 붙어 F를 눌러도 수령되지 않는 이유

> 시작하자마자 빌더로 생명선과 방벽을 구매한 후 보급 타워를 설치했는데, 러너가 해당 보급 타워에 붙어서 바라보며 F를 눌러 상호작용해도 아이템이 들어오지 않는 이유가 뭐야?

### 답변: 코드에서 확인된 소지 한도

기존 Runner 프리팹은 생명선과 방벽을 최대 수량으로 보유한 채 시작한다. 이번 작업에서는 초기 수량과 최대 소지량을 변경하지 않았다.

| 아이템 | 시작 수량 | 최대 소지량 |
|---|---:|---:|
| 생명선 | 3 | 3 |
| 방벽 | 99 | 99 |

빌더의 구매 가능 여부와 러너의 수령 가능 여부는 별도 판정이다. 빌더가 구매하고 타워에 적재했더라도 해당 러너 슬롯이 가득 차 있으면 추가를 거부한다. 수령되지 않은 항목은 보급타워에 남으며, 실제로 비었을 때만 타워를 제거한다.

생명선 또는 방벽을 하나 사용하면 해당 종류를 하나 받을 여유가 생긴다. 예를 들어 방벽만 하나 사용했다면 방벽 보급품만 받을 수 있고, 가득 찬 생명선은 타워에 남는 것이 현재 코드의 기대 동작이다.

근거:

- [Player Runner.prefab](../../Assets/03_Prefabs/Player/Player%20Runner.prefab): `_itemDefinitions`의 `InitialCount`/`MaxCount`.
- [RunnerItemSlot.cs](../../Assets/02_Scripts/Player/Player%20Runner/Item/RunnerItemSlot.cs): `Count >= MaxCount`이면 `TryAdd`가 false를 반환한다.
- [PlayerRunner.cs](../../Assets/02_Scripts/Player/Player%20Runner/Network/PlayerRunner.cs): `TryReceiveItemSupply`가 지정 슬롯에만 추가한다.
- [SupplyTower.cs](../../Assets/02_Scripts/Tower/Towers/Support%20Tower/SupplyTower.cs): 수령에 성공한 항목만 제거하며 나머지는 유지한다.

### 아직 확정하지 않은 부분: 실제 F 상호작용 도달 여부

사용자의 플레이에서 수령되지 않은 원인 전체를 소지 한도로 확정한 것은 아니다. 아이템을 사용하여 소지 여유를 만든 후에도 받지 못하면 다음 경로를 확인해야 한다.

1. `HandleInteractInput`은 캐릭터 위치에서 위로 1m인 지점에서 캐릭터 정면으로 3m Raycast를 쏜다. 카메라가 바라보는 방향과 동일하다고 보장되는 판정은 아니다.
2. 처음 맞힌 Collider 자체에서 `IRunnerInteractableTower`를 찾는다. 다른 Collider를 먼저 맞히거나 해당 Collider에 컴포넌트가 없으면 타워의 `Interact`에 도달하지 않는다.
3. 타워는 유효한 시뮬레이션 상태, State Authority, 같은 NetworkRunner, 살아 있는 러너, 거리, 적재 내용물을 검사한다.
4. `상호작용 사용` 로그는 Raycast 성공 여부와 무관하게 출력된다. 이 로그만으로 보급타워 상호작용 성공을 판단하면 안 된다.

원인 확인 순서는 **소지 여유 확보 → Raycast가 맞힌 Collider 확인 → 타워 Interact 호출 확인 → 실제 적재 ID와 권위 확인 → 슬롯 수량 및 HUD 확인**이다. 이번 질의응답 자체에서는 추가 수정이나 실제 재현 검증을 수행하지 않았다.

## 검증 상태와 후속 확인

컴파일, 규칙·인벤토리 검사, 프리팹 참조, 두 해상도의 UI 렌더링은 확인했다. Host 실행 시도는 테스트 진입의 Additive Scene 초기화 오류로 공급 시스템 준비에 도달하지 못했다. 실제 Host·Client 구매·건설·수령·Late Join 검증은 미완료이며, 위 기대 동작을 실제 플레이 검증 결과로 간주하지 않는다.

정상 Lobby 경유 두 Peer 세션에서 Host/Client 역할을 바꿔 재검증하는 절차는 관련 완료 작업 문서에 남겼다. 사용자 보고 증상의 해결 완료를 선언한 문서가 아니다.
